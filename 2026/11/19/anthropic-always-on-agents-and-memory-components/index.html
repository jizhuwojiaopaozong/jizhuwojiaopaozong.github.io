Always-on Agents 与 Agent Memory：Anthropic 两张蓝图——run 循环、五原语与 dreaming 记忆层级

发表于 2026-11-19 分类于 agent 阅读次数：
整合解读 Anthropic 两篇文章：always-on agent 的睡眠-run 循环与事件收件箱/定时器/记忆/权限/发件箱五原语，agent 记忆四层层级与 dreaming 巩固机制，及两者的串联架构

核心主线：Anthropic 两张蓝图拼出无人值守 agent 的完整骨架——《Building always-on agents》管「何时醒、带什么走、怎么送达」（run 循环 + 五原语），《The components of agent memory》管「记什么、怎么纠、怎么组织」（记忆层级 + dreaming）；后者其实是前者循环里一种特殊的定时 run。
本讲目标：读完你能回答「always-on 为什么是错觉、run 与 session 各是什么」「事件收件箱为什么必须存在、四条最佳实践各防什么故障」「记忆四层层级与 dreaming 的五种作用」「为什么固定记录规则反而伤害强模型」
课程来源：Building always-on agents（claude.com，William Hu，2026-11-13）与 The components of agent memory（anthropic.com/research，2026）两篇文章的整合解读

1. 两篇文章，一个问题：无人值守地长期运行

把两篇文章放在一起读，会发现它们回答的是同一个问题的两半：如何让 agent 在没有人盯着的情况下长期可靠地工作。第一篇给的是时间与控制的骨架——agent 何时被唤醒（事件收件箱、定时器）、每次运行携带什么（记忆）、行动边界在哪（权限）、工作结果如何到达用户（发件箱）。第二篇给的是记忆的骨架——什么值得写下来（显著性）、写错或写旧了怎么办（dreaming 纠正）、笔记如何长成可导航的知识（wiki 等表示）、哪些内容配得上每次会话都注入（层级顶端）。

两文的交汇点在于：记忆不是独立子系统，而是 run 循环里「读基线→行动→写回」的那一环；而 dreaming 本身也可以被实现为一种由定时器触发的、静默的特殊 run。先拆开看，再合起来看。

记住这个就够了：第一篇管循环与边界，第二篇管记忆与反思；合起来才是完整的 always-on 架构。

2. Always-on 是错觉：睡眠-运行循环

「Always-on」描述的是用户体验，不是进程状态：agent 大部分时间在睡觉（不花 token），周期性地醒来工作。每一段工作叫一次 run：接收一个事件、完成任务、把发生的事情写回存储；run 发生在 session 里，session 就是消息与工具调用的转录。run 结束 agent 回去睡，循环无限重复——「永远在线」的感觉来自循环不停，而不是进程不眠。

这个形态为什么现在才复活？文章给了两个模型侧的理由：一是判断力——新模型更可靠地理解用户意图、知道何时该来确认；二是智能变便宜，且长程任务受益最大——在一个长程编码基准上 Opus 5.5 每解决一个任务的成本比 Opus 5 低 78%，而普通负载只低 40%。换句话说，always-on 的可行性首先是经济学问题：睡眠时零成本，醒来时每次 run 的智力单价在快速下降。

记住这个就够了：run = 事件→工作→写回；session = 转录；always-on = 短 run 的无限循环 + 睡眠期零成本。

3. 五原语上：事件收件箱与定时器

事件收件箱（event inbox） 解决「谁来叫醒 agent」。最诱人的做法是让每个事件源直接调用 agent，但有两个致命故障模式：两个事件同时到达会启动相互竞争的 run；进程崩溃会彻底丢掉事件。于是架构变成三件套：一个持久化事件列表（通常是数据库表，每个事件追加一行、记录状态、按源端唯一标识去重）、一个 handler（HTTP 端点，只负责把事件写进列表）、一个 worker（后台服务，读列表、启动 run、等 run 结束、把事件标记完成）。建议从每用户一个 inbox 起步，需要更高并行度再拆。

四条最佳实践各自对应一种故障：handler 快速 ACK（webhook 提供方把慢响应当失败；prompt 注入这类深度检查留给 run 内做）；inbox 是唯一事实源（worker 醒来先拉最新事件，于是 worker 死在 run 中途时新 worker 能捡起同一事件重试）；一个 inbox 同时只有一个活跃 worker（防止两个 run 重复劳动或互相覆盖；run 中途来新事件有三种策略：推到下一次 run、折进当前 run、中断重启）；worker 批量合并待处理事件（用户连发多条消息合并成一次 run，只回一次）。

定时器（timers） 与收件箱配合产出「主动性」，分两类：follow-up 是 agent 给自己设的截止（比如稍后检查对方是否回复），schedule 是用户设的周期任务（比如每日简报）。关键设计：定时器住在独立于 inbox 的持久表里——inbox 只放「已经可以干活」的事件。scheduler 按固定间隔轮询：扫出到期的定时器→按类型更新（follow-up 标记完成；schedule 把到期时间推到下一次）→往 inbox 加一个事件并唤醒 worker。定时器自己从不直接启动 run，它只是往 inbox 投事件——这条纪律保证了唤醒路径只有一条。

记住这个就够了：inbox 三件套 + 四实践防竞争与丢事件；定时器独立存储、只投事件不启动 run，唤醒路径唯一。

4. 五原语下：权限与发件箱

权限（permissions） 是 always-on agent 风险最集中处：一次 run 持有用户的访问权限，且按设计无人值守。每个工具调用都要三选一：自己继续、阻断、或等待批准。三个组件：凭据存储用环境外代理模式——agent 发出不含凭据的请求，代理在转发前注入真实凭据，凭据从不进入 agent 环境；auto mode 用分类器审查高风险动作、阻断被判定危险的调用让 Claude 换更安全的路径，但最重要的决定仍留给人；deferred tool calls 是最精巧的闭环——hook 把某个工具调用挂起，run 结束、session 保存在调用中途，请求以交互卡片形式展示给用户，用户的回答作为 inbox 里的一个事件回来，启动新 run 恢复被保存的 session；等待期间 worker 可以处理其他事件，agent 不被阻塞。注意这个设计把「等人」变成了「睡觉」：审批等待不占用 run。

发件箱（outbox） 对应输出侧：后台工作的 agent 不该把逐步推理流式倒给用户，用户要的是结果加少量细节。一次 run 有三种结束方式：往 outbox 发消息、决定什么都不发、或用 deferred tool call 请求批准/补充输入。多数 agent 一个「send」工具就够；只有需要控制消息节奏或从发送错误中恢复时才建正式 outbox——一张出站消息表加一个 dispatcher 后台服务（与 inbox/worker 对称）。节奏靠 evals 调：发太多是噪音，发太少漏事；实践建议先安静，再逐渐挣得用户的注意力。

记住这个就够了：凭据走环境外代理、高风险走分类器、审批走 deferred call 变事件；输出侧先安静、按需建 outbox。

5. 记忆工程：只存查不回来的东西

第一篇对记忆的工程原则只有一句狠话：memory 只放 agent 无法再次查到的东西；已经活在别的系统里的（比如 issue tracker），存指针而不是副本。记忆要有自己的存储，目录映射到持久化（数据库或对象存储），保证记忆比 worker 活得更久。

四类记忆各有加载策略：

  • 用户指令：关于 agent 行为的指示，独立文件，每次 run 开头加载——用户不会总在旁边纠偏，指令必须跨 run 携带
  • 用户笔记：关于用户本人的所学（角色、偏好、纠正）；起步一个文件，长大后拆成多个小文件，每次 run 只加载索引，需要细节时再拉单个文件进上下文
  • 过往消息：记录已经告诉过用户什么，避免重复；独立文件每次加载，或由 worker 载入最近几条消息
  • 任务进度：每个进行中任务一个进度文件（已做/待做），新 run 读它即可接续；同样索引常载、详情按需

「索引常载、详情按需」是贯穿两篇文章的记忆经济学：上下文是稀缺资源，常驻的只能是地图，不能是领土。

记住这个就够了：存不可再查者、其余存指针；四类记忆两种加载策略（常载 vs 索引+按需）。

6. 记忆层级与 dreaming：agent 的睡眠

第二篇给出四层记忆层级（自底向上）：transcripts（可搜索的事件日志）→ memory notes（Claude 写下的显著观察）→ memory representations（如 wiki 这类组织化表示）→ injected context（每次会话开头预载的上下文）。并明确划界：这里说的 memory 不含权重改变、不含单会话内的 in-context learning、不含 compaction 摘要——它是跨会话留存、以可读上下文形式存在的经验知识。

生物学类比是设计直觉的来源：海马体在经历发生的当下快速捕获记忆，而巩固（consolidation）主要发生在离线时段——睡眠与静息中海马体重放近期经历，把经验蒸馏进存储知识的新皮层。Agent 的对应物：transcripts 是海马体的原始捕获，dreaming 是离线重放与巩固——利用交互间的空闲时间反思日志、纠正错误、产出新笔记与新表示（思路源自 Letta 与 UC Berkeley 的 sleep-time compute）。层级图上 dreaming 的箭头从 transcripts 指向上面每一层，并在相邻上层之间双向——它既能从原始日志提炼笔记，也能在笔记、表示、注入层之间搬运和修剪。

Dreaming 的五种作用在后文逐一有实验支撑：纠正错误笔记、构建新表示（wiki）、提升笔记到注入层、聚焦记忆服务于特定目标、填补会话遗留的缺口（如悬空链接）。

记住这个就够了：四层层级 + 离线巩固：dreaming 把「当下写的笔记」变成「经得起未来信任的知识」。

7. 写什么是一种预测：显著性与学习闭环

「记忆偶尔是一种预测」：写下一条规则，是预测这个模式还会相关；写下一条已验证事实，是预测未来会话想直接依赖它而不再复核。于是显著性判断成为记忆系统的第一能力——而难处在于：写笔记的当下并不知道未来需要什么。

CL-Bench 1.0 的数据库任务展示了学习闭环的模型阶梯（每问一个新会话 + 跨会话记忆目录）：答错→记录失败→提出理论→验证理论→沉淀为规则。各代模型停在阶梯不同位置：Sonnet 4.6 只到「提出理论」，记忆目录里散落着未验证的猜测（0.330→0.364）；Opus 4.7 把笔记 consolidat 成单一参考文档并标记已查/未查（0.383→0.700）；Sonnet 5 会在评分后标记 confirmed 并写纠正（0.644→0.833）；Opus 5 第一个闭环——条目含规则、规则的依据、过往答案与陷阱警告（0.564→0.828）；Opus 5.5 与 Sonnet 5.5 同样闭环（0.655→0.838、0.644→0.833）。

Pokémon Red 实验则考「什么值得记」：Sonnet 3.7 假设一切都可能重要，无差别写入——413 个文件、225 个文件夹、约 97.8 万字符，换 1 枚徽章；因为游戏状态 constantly 变化，详尽记录持续过期，agent 花越来越多时间翻记忆而非玩游戏（约第 10000 步时它用 17 步创建 6 个文件、删除 9 个、游戏内零动作）。Fable 5 只写 9 个文件加一个 global.md 仪表盘（当前目标、道馆计划、自用记忆规则），4.3 万字符，4 枚徽章——它只记游戏不会告诉它的东西（策略、计划、验证过的规则），屏幕上每回合能读到的（钱、位置）一律不存。Opus 5.5 同样小文件夹策略并通关。

引导原则因此很反直觉：告诉 Claude 记忆是为什么，但别规定怎么用。固定规则甚至有害：「只记录失败」让 Opus 5 的记忆增益 −0.234、Opus 4.7 −0.150——强模型的显著性自由裁量胜过预设规则。引导对老模型帮助最大：提示 Sonnet 4.6 先读记忆、再显式验证理论，分数几乎翻倍（0.364→0.641）；而 Sonnet 5 不需要提示就 9/10 次主动读记忆。

记住这个就够了：写记忆=下预测注；显著性靠模型自由裁量（强模型），固定规则反噬；只记查不回来的、会过期的不记。

8. 数字与边界：wiki 何时有效何时失效

Dreaming 构建表示的代表是 wiki：Claude 自写自维护的互链页面集合，链接构成导航地图。Stainless 语料（约 35 万文件、约 4.2 亿 token）上 128 个会话的 dreaming 把 25 问的得分从 13% 拉到 48%（仅 wiki）；wiki+搜索从 54% 到 61%，而仅搜索持平在 53%——表示与检索互补而非替代，且 wiki+搜索每问省约 2 万 token。wiki 图从 2 会话的 103 页/766 链长到 128 会话的 222 页/12893 链。

何时有效有清晰画像：Harvey LAB 合并案中 24 问过半需要跨文档组合加判断/计算，wiki 87% vs 仅搜索 73%；而当评分标准大多能在单个文档里文本搜到时，wiki 无增益。失效模式同样鲜明：一个任务里 wiki 长到比语料还大（10 文档 115KB → wiki 68 页 203KB，1.77 倍）——Borges 笔下与帝国等大的地图：什么都没抽象。另一类失效是协作写坏：四个 agent 同时写共享的条款表、互相覆盖，57 个评分事实只活下 41 个（72%）；让 Claude 反思失败→改指令→重建 wiki 的循环发现「条款须逐字引用、每合同独立页」后，57/57 全活（100%）。

注入层（层级顶端）的纪律：注入的记忆每次会话都花 token，一条错笔记会被带进每个会话，且加载不等于遵循（Claude Code 文档警告指令文件越长遵循率越低）。所以顶端必须保持小：Claude Code auto memory 每次只载 MEMORY.md 的前 200 行或 25KB 作为索引头；dreaming 的大量工作正是把细节往下层搬、只留链接。

记住这个就够了：wiki 赢在跨文档组合、输给单文档可搜与「等大地图」；注入层配额化（200 行/25KB），dreaming 负责修剪。

9. 串联两张蓝图：dreaming 就是循环里的一种 run

把第二篇塞回第一篇的循环，架构立刻自洽：dreaming 不过是一次由定时器触发的特殊 run——事件来自 scheduler（而非用户或 webhook），session 里读的是 transcripts 与现有记忆（对应「读基线」），写回的是笔记/wiki/注入层（对应「更新记忆」），outbox 通常静默（对应「决定什么都不发」）。它同样享受 inbox 的持久化与单 worker 纪律，同样受权限约束（dreaming 不该有对外动作的凭据）。

反过来，第一篇的记忆四分类也能在层级里定位：用户指令与索引属于注入层（每次 run 开头加载），用户笔记与任务进度属于 notes 层（索引常载、详情按需），过往消息可由 transcripts 层兜底。deferred tool call 则是两篇共同隐含的「人在环中」接缝：把审批变成 inbox 事件，等于承认有些显著性只有人类能判断——与第二篇「最重要决定仍需人工审查」呼应。

由此得到一个可操作的架构命题：always-on agent 的质量上限不取决于单次 run 的智力，而取决于睡眠期把经验整理成什么——循环提供原料（transcripts），dreaming 提供巩固，注入层提供起跑线；三者配比就是记忆系统的调参空间（dreaming 频率、注入配额、wiki 修剪力度）。

记住这个就够了：dreaming = 定时器触发的静默 run；记忆四分类 = 层级四层的工程实例；人在环中 = deferred call 事件化。

10. 收尾：落地检查清单

把两篇的全部纪律压成一张清单：持久 inbox + 快速 ACK + 单活跃 worker + 事件批量合并；定时器独立存储、只投事件；记忆独立持久存储、只存不可再查者、索引常载详情按需；凭据环境外代理、高风险分类器、审批 deferred 化；outbox 先安静后挣注意力、节奏靠 evals；dreaming 定期跑、对着 transcripts 纠错、wiki 修剪防等大地图；注入层配额 200 行/25KB；对强模型只说记忆为何、不规定怎么用。

如果资源只够先做三件事，优先级是：inbox 持久化（丢一个事件就是一次不可恢复的信任损失）、记忆索引常载+详情按需（上下文预算决定 run 的智商上限）、注入层配额（一条错笔记污染所有会话，且越长越不遵循）。其余项可以随规模补齐，但这三项是循环能转起来的前提。

清单之外还有一个元纪律：每次事故后回问「它属于十项里的哪一项失效」——两篇文章的全部最佳实践都来自真实故障模式（竞争 run、崩溃丢事件、记忆过期、wiki 互覆、噪音消息），检查清单的价值在于把故障模式变成验收项。

记住这个就够了：清单十项全绿，才谈得上「always-on」；缺任何一项，循环都会在某个深夜以丢事件、错记忆或噪音消息的形式讨债。

本讲小结

机制/概念 解决什么问题 一句话
睡眠-run 循环 无人值守的成本与可靠性 睡眠零成本，run 短而循环无限
事件收件箱 并发竞争与崩溃丢事件 持久表+handler+worker，inbox 为事实源
Deferred tool call 无人值守下的审批 挂起调用、session 存中途、批准变 inbox 事件
记忆层级+dreaming 笔记会错会旧、知识难导航 离线对照 transcripts 纠错、建 wiki、修剪注入层

学完能说的 3 句话：

  1. Always-on 是短 run 的无限循环：inbox 管唤醒、timers 管主动、memory 管携带、permissions 管边界、outbox 管送达。
  2. Agent 记忆是四层层级加离线巩固：dreaming 用空闲算力对照 transcripts 纠错、建表示、修剪注入层。
  3. 写记忆是下预测注：强模型靠自由裁量判断显著性，固定规则（如只记失败）实测降低记忆增益。

自测题（面试速答）

  1. 为什么不能让事件源直接调用 agent？收件箱三件套与四条最佳实践各防什么故障？（对应：事件收件箱）

答案： 直接调用有两个致命故障：并发事件启动相互竞争的 run（重复劳动、互相覆盖），进程崩溃彻底丢失事件。三件套（持久事件表、写表的 handler、读表的 worker）把「到达」与「处理」解耦；四条实践分别防：handler 快速 ACK 防 webhook 提供方把慢响应当失败；inbox 为事实源使 worker 崩溃后新 worker 可捡同一事件重试；单活跃 worker 防并发 run 互相覆盖；批量合并防用户连发消息触发多次 run。定时器也只往 inbox 投事件，保证唤醒路径唯一、可审计。

  1. 记忆层级自底向上四层是什么？dreaming 在层间做哪五件事？（对应：记忆层级）

答案： 四层是 transcripts（可搜索事件日志）、memory notes（会话内写下的显著观察）、memory representations（wiki 等组织化表示）、injected context（每次会话预载的顶端上下文）。Dreaming 利用离线算力做五件事：对照 transcripts 纠正错误笔记、构建 wiki 等新表示、把笔记提升到注入层、按特定目标聚焦记忆生长、填补跨会话遗留缺口（如悬空链接）。顶端必须配额化（如 MEMORY.md 前 200 行/25KB），因为注入内容每次会话都花 token 且错笔记会被带进每个会话。

  1. 为什么「只记录失败」这类固定规则反而降低强模型的记忆收益？Pokémon 对比说明了什么？（对应：显著性判断）

答案： 因为写记忆本质是对未来需求的预测，预设规则砍掉了模型对显著性的自由裁量：实测「只记失败」使 Opus 5 记忆增益 −0.234、Opus 4.7 −0.150，而只告知「有记忆文件夹可用」就足以让强模型有效使用。Pokémon 对比说明显著性判断的另一面——记什么比记多少重要：Sonnet 3.7 无差别写 413 个文件（多为屏幕上随时可读、且持续过期的状态）只得 1 徽章还陷入翻记忆的空转；Fable 5 只写 9 个文件（策略、计划、验证过的规则）得 4 徽章。即：只记查不回来的、会过期的不记。
